# Implemented vertical-slice boundaries
Browser/BFF (not yet included) authenticates with Keycloak. User access JWT `aud=demo-api` goes to demo API. Demo API validates it, queries `widgets WHERE tenant_id=? AND id=?`, then calls IAM using service-account JWT `aud=iam-api`; IAM independently validates end-user token and scoped membership/permission. IAM does not inspect widget ownership; demo API must keep scoped query. Admin identity uses access JWT `aud=iam-api`; platform admin identity is seeded out of band by issuer+sub.

Application DB tables: identities, tenants, products, tenant_products, memberships, permissions, roles, role_permissions, role_assignments, platform_admins, audit_events, outbox. Demo product database has widgets only. Keycloak uses separate database. All IAM decisions are online DB checks and fail closed; there is no cache so latency target must be measured. Audit/outbox rows inserted atomically in IAM mutations but no worker or immutable sink yet. No user credentials in application schema.

In pilot, create-tenant owner must equal authenticated platform-admin subject; no accidental orphan owner or silent linking by email. Other membership provisioning and owner transfer are deliberately blocked until verified invitation/approval workflow is implemented. This is safer than a half-built invite endpoint. APIs bind admin authority to a user token and service authority to Keycloak `azp`/`client_id` **plus pinned service subject**, scoped to product ID.
